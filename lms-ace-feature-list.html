Evergreen Self-Service Training LMS

A web-based learning management system where administrators prepare and publish long-lived training courses, students independently enroll and pay through Stripe, study the preloaded materials step by step, and automatically receive a certificate only after the LMS verifies 100% completion of all required learning items.

Primary modelCourse → Enrollment → Stripe payment → Learning → 100% → Certificate Operating modelSelf-service · no trainers · no live teaching · no active learner monitoring ContentVideo · Interactive video · PDF · PPT/PPTX · Text · Files · Images · Links · Quizzes PaymentsStripe Checkout + verified webhooks CertificatesAutomatic digital/PDF certificate at 100% LifecycleCourses are designed to remain usable for many years
Core operating principle: Once a course is published, the LMS itself delivers the learning journey. Students do not need a trainer, instructor, mentor, or staff member to guide them through the course. The course contains the learning materials, completion rules and certificate configuration needed for independent completion.
Automatic journey: Admin creates or updates course → course is published → student opens course link/QR → registers/signs in → enrolls → pays through Stripe → verified payment unlocks access → student studies materials step by step → LMS records completion → progress reaches exactly 100% → certificate is generated automatically.
Certificate rule: Opening a course, reaching the last lesson, watching some content, or changing browser-side values must never be enough to issue a certificate. The server-side completion engine must verify every required learning condition and issue the certificate only when the final progress state is 100%.

07

Payments & Stripe Integration critical

Stripe Checkout is the payment layer. Course access is granted only after the server receives and verifies the relevant Stripe webhook event.

Never unlock paid content solely because the student returned to a success URL. The verified server-side payment event is the source of truth for paid access.
StageBehaviour
1. Start enrollmentStudent selects the course and signs in/registers.
2. Create checkout sessionServer creates the Stripe Checkout Session using the authoritative course price.
3. Stripe checkoutStudent completes payment in the Stripe-hosted checkout experience or approved integration.
4. Return pageStudent returns to the LMS. The page explains that payment confirmation is being checked.
5. WebhookStripe sends the payment event to the LMS webhook endpoint.
6. VerificationServer verifies the webhook signature against the raw request body.
7. IdempotencyRepeated webhook deliveries do not create duplicate payment or enrollment records.
8. FulfillmentMark payment paid, activate enrollment and grant access to the purchased course version.
9. FailureFailed or expired payment does not grant paid course access.

Payment states

StateMeaning
PendingEnrollment started but successful payment is not confirmed.
Checkout createdStripe Checkout Session created.
PaidSuccessful payment confirmed by verified Stripe event.
FailedPayment attempt failed.
ExpiredCheckout session expired before successful payment.
RefundedStripe payment refunded; access follows the configured refund policy.

Developer requirements

  • Keep Stripe secret keys server-side only.
  • Use environment variables or secure secret storage.
  • Verify webhook signatures against the raw request body.
  • Persist Stripe customer, checkout session and payment identifiers.
  • Store internal enrollment/course identifiers in Checkout metadata.
  • Use Stripe event IDs for idempotent processing.
  • Never trust a price supplied by the browser; fetch the authoritative course price from the server.

16

100% Completion & Automatic Certificate

Progress calculation

course_completion_percentage = completed_required_learning_items / total_required_learning_items × 100 certificate_eligible = course_completion_percentage == 100% AND all_required_completion_rules_are_satisfied

The implementation may use lesson weights or another deterministic model, but the final result must always be reproducible and server-authoritative.

ScenarioExpected result
Student opens a courseProgress does not automatically become complete.
Student watches part of required videoVideo remains incomplete until the configured threshold is met.
Student passes required quizQuiz becomes complete.
Student completes all required itemsProgress becomes 100%.
Progress reaches 100%Enrollment is marked completed exactly once and certificate issuance starts automatically.
Certificate generatedCertificate is stored permanently with student, course, course version and unique certificate number.
Student returns laterCourse remains completed and certificate remains available.
Absolute business rule: 100% completion is the single eligibility threshold for automatic certification. There is no separate trainer sign-off, manual approval or attendance confirmation in the normal LMS workflow.

VERSION

Course Versioning & Long-Term Content

Courses are expected to remain useful for many years. Publishing a new version must therefore preserve the integrity of historical enrollments and already-issued certificates.

Recommended rule: Published course versions behave as immutable snapshots. New edits happen in a new draft version. New students receive the newest published version. Existing students remain attached to the version they enrolled in unless the organisation explicitly defines a migration rule.
StepBehaviour
1. Edit published courseCreate a new draft version instead of modifying the historical published snapshot in place.
2. Edit draftChange lessons, files, videos, quiz settings, resources and wording.
3. ValidateEnsure required learning items, completion rules and certificate configuration remain valid.
4. PublishNew version becomes the default version for future enrollments.
5. Existing studentsRemain attached to their enrolled version by default, preserving their progress.
6. Historical certificatesRemain permanently tied to the exact course version completed.
7. Update noticeOptional automatic notice can inform existing students that a newer version exists; this must not create a manual monitoring workflow.

Why versioning matters

A ten-year course library must not change underneath a learner in a way that invalidates their progress or makes an old certificate point to content they never completed. Versioned snapshots provide that stability.

QA

Developer Acceptance Criteria

  1. Admin can create a course with title, description, thumbnail, price and stable public URL.
  2. Admin can create modules/sections and reorder them.
  3. Admin can create lessons using video, interactive video, text, PDF, PPT/PPTX, resources, images, links, checklists and quizzes.
  4. Admin can configure which learning items are required and define their completion rules.
  5. A published course can be updated through a new version without corrupting historical enrollments or certificates.
  6. New students receive the latest published course version by default.
  7. There is no trainer/instructor workflow required for a student to complete a course.
  8. There is no normal manual approval step for completion or certification.
  9. Student can open a course through its public link or QR code.
  10. Student can register/sign in and start enrollment.
  11. Paid enrollment creates a Stripe Checkout Session using server-controlled pricing.
  12. Paid access is granted only after verified Stripe webhook processing.
  13. Repeated Stripe webhook events do not create duplicates.
  14. Student can access the purchased course and resume where they left off.
  15. Required learning completion is enforced server-side.
  16. Changing browser-side progress values cannot produce false completion.
  17. Course progress becomes exactly 100% only when every required completion condition is satisfied.
  18. When progress reaches 100%, enrollment becomes completed exactly once.
  19. Certificate generation starts automatically after 100% completion without staff approval.
  20. Certificate is generated using the exact course version completed.
  21. Certificate number is unique and the certificate can be viewed/downloaded by the student.
  22. Refreshing or revisiting a completion page cannot generate duplicate certificates.
  23. Public certificate verification works when enabled.
  24. Course materials can remain available for long-term use through durable storage and versioned content.
  25. Large media processing, emails and certificate generation do not block the learner-facing request.
  26. Admin screens remain usable for large course libraries and large enrollment tables.
  27. Core public, student and admin interfaces target WCAG 2.2 AA.
